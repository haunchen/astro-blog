# Article Blocks

文章正文裡依 h2 標題套用版型的三種區塊（常見問題、故障排除、文末連結），以及確保文章寫法符合這套約定的結構檢查。

## Requirements

### R1: 常見問題區塊的辨識
- **Level**: MUST
- **Description**: 文章正文中，文字含「常見問題」的 h2 到下一個 h2 之前的範圍是常見問題區塊。節內每個 h3 是一題，h3 之後到下一個 h3 之前的內容是該題的答案。第一個 h3 之前的內容是引言，不屬於任何一題。

### R2: 常見問題區塊以風琴呈現
- **Level**: MUST
- **Description**: 常見問題區塊的所有題目被框成一個區塊，每題一列、列與列之間有分隔線。每題預設收合，點題目列展開或收合答案；各題獨立，可同時展開多題。引言顯示在框外。開合不依賴 JavaScript，也沒有過場動畫。

### R3: 故障排除區塊
- **Level**: MUST
- **Description**: 文字以「故障排除」開頭的 h2，其後到下一個 h2 之前的內容整體框成一個區塊，內容本身不變。h2 同時含「常見問題」時視為常見問題區塊。

### R4: 文末連結區塊
- **Level**: MUST
- **Description**: 文字等於「參考資料與延伸閱讀」的 h2，其後到下一個 h2 之前的內容整體框成一個區塊，內容本身不變。一篇文章的外部來源與站內延伸閱讀只放在這一節。

### R5: 區塊外觀與既有區塊可區分
- **Level**: MUST
- **Description**: 三種區塊的框使用次要底色、細邊框與圓角，不使用左側橘色粗線——那是引言（blockquote）與更新紀錄的外觀。三種區塊的 h2 都留在框外。

### R6: 目錄與錨點行為不變
- **Level**: MUST
- **Description**: 區塊內的 h2、h3 保留原本的 id，照常出現在側邊目錄。從目錄或錨點連結到某一題時，頁面捲到該題的題目列；題目列在收合狀態下仍然可見。

### R7: 版型不影響 markdown 變體
- **Level**: MUST
- **Description**: 文章的 `.md` 變體與 `Accept: text/markdown` 的協商回應不含任何因區塊版型而加入的標記，內容與原始 markdown 的問答、連結一致。

### R8: 結構檢查的規則
- **Level**: MUST
- **Description**: 結構檢查對一篇文章的 markdown 回報下列違規：(E1) 常見問題區塊內沒有任何 h3；(E2) 常見問題區塊內有整段粗體的段落；(E3) 常見問題區塊內的 h3 含「總結／結語／下一步／學習路徑／延伸閱讀」；(E4) h2 使用別名——「常見問答」、不含「常見問題」的「FAQ」或「Q&A」、以「疑難排解」或「問題排解」開頭；(E5) 一篇有兩個以上常見問題區塊；(E6) h2 以「參考資料／參考資源／延伸閱讀」開頭但不等於「參考資料與延伸閱讀」，或該標題出現兩次以上。

### R9: 結構檢查的執行點
- **Level**: MUST
- **Description**: 結構檢查在三處執行：`sync-from-vault` 的 dry-run 報告逐篇列出違規，`--apply` 不寫入有違規的文章且結束碼非零；pre-commit 檢查這次 staged 的文章，有違規則擋下 commit；PR 的 CI 檢查全部文章，有違規則失敗。

### R10: 寫作約定與版型一致
- **Level**: MUST
- **Description**: 版型的區塊辨識與結構檢查對同一個 h2 的判定永遠一致：檢查放行的文章，頁面上一定套到對應版型。

## Scenarios

### S1: 讀者閱讀常見問題
- **Given**: 一篇文章有常見問題區塊，節內有引言與數題
- **When**: 讀者開啟文章頁並捲到該節
- **Then**: 引言顯示在框外；所有題目在同一個框內各佔一列且答案收合；點任一題的題目列展開該題答案，其他題的狀態不變
- **Implements**: #R1, #R2, #R5

### S2: 從目錄跳到某一題
- **Given**: 一篇文章有常見問題區塊
- **When**: 讀者點側邊目錄中的某一題
- **Then**: 頁面捲到該題的題目列，該題維持收合
- **Implements**: #R6

### S3: 同時含兩個關鍵詞的標題
- **Given**: 一篇文章的 h2 同時含「常見問題」與「故障排除」
- **When**: 開啟文章頁
- **Then**: 該節以風琴呈現
- **Implements**: #R1, #R3

### S4: 故障排除與文末連結
- **Given**: 一篇文章有故障排除區塊與文末連結區塊
- **When**: 開啟文章頁
- **Then**: 兩節的 h2 在框外，其下內容各自在一個框內，內容與框起來之前相同
- **Implements**: #R3, #R4, #R5

### S5: agent 取得 markdown 變體
- **Given**: 一篇文章有三種區塊
- **When**: 請求該文章的 `.md` 變體
- **Then**: 回應是原始 markdown 的標題、問答與連結，沒有風琴或框的標記
- **Implements**: #R7

### S6: 落地不合規的草稿
- **Given**: vault 的一篇草稿有 R8 所列的任一違規
- **When**: 執行 `sync-from-vault`（dry-run，然後 `--apply`）
- **Then**: dry-run 報告列出該篇的違規；`--apply` 不寫入該篇，結束碼非零
- **Implements**: #R8, #R9

### S7: 在 repo 直接改稿
- **Given**: 一篇 staged 的文章有 R8 所列的任一違規
- **When**: 執行 `git commit`
- **Then**: commit 被擋下，輸出指出哪一篇、哪一條違規
- **Implements**: #R8, #R9

## Design Decisions

### D1: 以 h2 標題文字辨識區塊
- **Decision**: 區塊由 h2 的文字決定，不用 markdown directive 或 frontmatter 宣告
- **Rationale**: 寫稿不必多記語法，Obsidian 裡是普通標題，`.md` 變體維持乾淨。directive 需要額外依賴、Obsidian 不認得、還會漏進 `.md` 變體；frontmatter 宣告在標題改名後會對不上
- **Date**: 2026-11-26

### D2: 常見問題與故障排除分開定義
- **Decision**: 針對整篇文章的問答用風琴；跟著操作主題走的排錯或注意事項只框起來
- **Rationale**: 排錯章節的內容是症狀與處置、常帶程式碼，逐項收合不合適；兩者在既有文章裡的位置與寫法也不同
- **Date**: 2026-11-26

### D3: 題目寫成 h3，不寫粗體段落
- **Decision**: 常見問題的題目一律是 `### 問題`，不寫 `**Q1：…**`，不加編號
- **Rationale**: 粗體段落與正文的粗體句無法區分，版型與檢查都只能猜；h3 是確定的元素邊界
- **Date**: 2026-11-26

### D4: 預設全部收合、各題獨立
- **Decision**: 不預設展開任何一題，也不做一次只開一題
- **Rationale**: 可以同時展開多題對照；純原生 `<details>`，所有瀏覽器行為一致
- **Date**: 2026-11-26

### D5: 目錄跳題不自動展開
- **Decision**: 從目錄或錨點到某一題時不自動展開答案
- **Rationale**: 自動展開需要 JavaScript；題目列在收合時仍可見，跳轉不會落空
- **Date**: 2026-11-26

### D6: 文末連結只有一個標題
- **Decision**: 統一為「參考資料與延伸閱讀」，只有外部來源或只有站內連結的文章也用完整標題
- **Rationale**: 文末一律一個框、一種寫法；沿用多數既有文章的用字，改動與錨點變更最少
- **Date**: 2026-11-26

### D7: 檢查邏輯只在 repo
- **Decision**: 結構檢查只有 repo 的一份實作，vault 的 blog plugin 只改文字約定，`preflight.py` 不重寫
- **Rationale**: 兩份實作會分歧；`blog:publish` 流程中 dry-run 緊接在 preflight 之後，提早兩步的效益小
- **Date**: 2026-11-26
